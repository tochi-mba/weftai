How it works

Define an operation once. Everything else is derived.

The same library, with the same plan format, is published for TypeScript on npm and for Python 3.12+ on PyPI.

01

You define operations

A name, a description for the model, an input schema, an output type and a handler. Standard operations per collection come for nothing: filter, count, countBy, distinct, mostCommon, first, pick, details.

02

The model writes a plan

Named steps over your operations. A later step refers to an earlier result as $stepId or $stepId[2]; positions always index the full set, not the preview the model was shown.

03

Your application runs it

If a plan has any issue, no step runs, and the model reads every issue at once. Independent reads run together, a write runs on its own in the order it was written, a failed step skips only its dependents, and every step is traced.

Rules it keeps

Rules that are part of the product.

Does my data travel through the model?

No. Results flow between steps by reference and stay in a session-scoped store. The model reads a formatted, token-budgeted view with exact counts, and refers to the full set by name.

What happens when the model asks a wrong question?

It is an error, never an empty result. An unknown field lists the available fields, an unknown step suggests the nearest id, and a reference written into a field that does not take one is refused before anything runs.

Is it tied to one model provider?

No. The plan tool is described once and adapted to each provider's wire format. A model that cannot call tools is an error naming the fix, and an unknown model name is not assumed to speak Chat Completions.

Does it force the model to call it?

No. No adapter sets a forced tool choice by default; the newest OpenAI, Anthropic and Gemini models reject one.
